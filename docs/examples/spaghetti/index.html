Spaghetti vs. mitsukeru

1. Coding the same behavior in different ways

Traditional product bundling or allocation logic intertwines search iterations with arbitrary branch conditions. Adopting a structured schema transforms rule handling from code refactoring to declarative configuration.

Existing Code 
const products = [
  { id: "A", price: 3000, score: 90, stock: 5 },
  { id: "B", price: 2000, score: 70, stock: 5 },
  { id: "C", price: 4000, score: 80, stock: 5 },
  { id: "D", price: 3000, score: 60, stock: 5 },
];
const budget = 10000;

let best = [], bestScore = 0;

for (let mask = 0; mask < (1 << products.length); mask++) {
  const selected = products.filter((_, i) => mask & (1 << i));
  const totalPrice = selected.reduce((sum, p) => sum + p.price, 0);
  const totalScore = selected.reduce((sum, p) => sum + p.score, 0);
  const ids = selected.map(p => p.id);

  // Business rules directly hardcoded into loop control
  if (totalPrice > budget) continue;
  if (selected.some(p => p.stock <= 0)) continue;
  if (ids.includes("A") && !ids.includes("B")) continue;
  if (ids.includes("C") && ids.includes("D")) continue;

  if (totalScore > bestScore) {
    best = selected;
    bestScore = totalScore;
  }
}

console.log("Best solution:", best);
console.log("Best score:", bestScore);
mitsukeru 
import init, { optimize } from "mitsukeru";
await init();

// Input payload conforms to Optimization Request schema
const solution = optimize({
  capacities: [10000], // Budget limit (10,000)
  items: [
    { id: 0, name: "A", weights: [3000], value: 90 },
    { id: 1, name: "B", weights: [2000], value: 70 },
    { id: 2, name: "C", weights: [4000], value: 80 },
    { id: 3, name: "D", weights: [3000], value: 60 }
  ],
  rules: [
    // A requires B
    { type: "requires", from_id: 0, to_id: 1 },
    // C conflicts with D
    { type: "conflicts", a_id: 2, b_id: 3 }
  ],
  config: { strategy: "mixed", time_limit_ms: 2.0 }
});

console.log("Best value:", solution.best_value);
console.log("Selected item IDs:", solution.selected_item_ids);

If there comes a time when you are no longer satisfied with this code, you will end up with various differences; as the number of such instances grows, maintaining the code using traditional methods will become increasingly difficult.

However, in simple cases, existing code with clear branching logic might be easier to follow. On the other hand, maintainability becomes a different matter in scenarios such as the following: when a change to a condition has an impact across the entire project, or when developers are repeatedly forced to add or rewrite similar if/else statements.

Below, a maximum shipping weight limit of 15 kg has been introduced, and a new item—Item E—has been added to the campaign. Item E must be used in combination with Item A, but it cannot be used together with Item D.

Existing Code 
const products = [
  { id: "A", price: 3000, weight: 5, type: "MAIN", score: 90, stock: 5 },
  { id: "B", price: 2000, weight: 3, type: "SUB",  score: 70, stock: 5 },
  { id: "C", price: 4000, weight: 6, type: "MAIN", score: 80, stock: 5 },
  { id: "D", price: 3000, weight: 4, type: "SUB",  score: 60, stock: 5 },
  { id: "E", price: 2500, weight: 4, type: "CAMPAIGN", score: 75, stock: 5 },];
const budget = 10000;
const maxWeight = 15; // Added maximum shipping weight limit

let best = [], bestScore = 0;

for (let mask = 0; mask < (1 << products.length); mask++) {
  const selected = products.filter((_, i) => mask & (1 << i));
  const totalPrice = selected.reduce((sum, p) => sum + p.price, 0);
  const totalWeight = selected.reduce((sum, p) => sum + p.weight, 0);
  const totalScore = selected.reduce((sum, p) => sum + p.score, 0);
  const ids = selected.map(p => p.id);

  // Business rules directly hardcoded into loop control
  if (totalPrice > budget) continue;
  if (totalWeight > maxWeight) continue;
  if (selected.some(p => p.stock <= 0)) continue;
  if (ids.includes("A") && !ids.includes("B")) continue;
  if (ids.includes("C") && ids.includes("D")) continue;

  let isViolated = false;
  for (const item of selected) {
    switch (item.type) {
      case "CAMPAIGN":
        if (item.id === "E") {
          if (!ids.includes("A")) {
            isViolated = true;
          } else if (ids.includes("D")) {
            isViolated = true;
          }
        }
        break;
      default:
        break;
    }
    if (isViolated) break;
  }
  if (isViolated) continue;

  if (totalScore > bestScore) {
    best = selected;
    bestScore = totalScore;
  }
}

console.log("Best score:", bestScore);

At this point, mitsukeru has already delivered results that go well beyond what could be captured by the existing codebase—such as providing the top k alternatives, indicating the percentage of the search space remaining, and detailing any contradictions that have arisen.

In this way, transitioning from procedural nested loops to an external solver shifts organizational velocity from code commits to parametric adjustments.

2. Things to consider before using mitsukeru unconditionally

Business requirements exhibit distinct computational traits. Knapsack engines must not evaluate contextual eligibility (e.g., promotional campaigns or membership tiers), and rule engines must not perform combinatorial branch-and-bound searches.

Modification Scenario Constraint Archetype Imperative Burden mitsukeru Declarative Schema Mapping
Add Product E with requirement on C Dependency Append nested guard: if (ids.includes("E") && !ids.includes("C")) { type: "requires", from_id: 4, to_id: 2 }
Mutual exclusion between B and E Mutual Exclusion Append guard: if (ids.includes("B") && ids.includes("E")) { type: "conflicts", a_id: 1, b_id: 4 }
Product D requires active campaign Pre-Eligibility Context check inside recursive combinatorial loop Pre-filtered by upstream engine (json-rules-engine)
Expand budget limit: $1,000 → $1,200 Multi-Cap Metric Modify global constant or state configuration capacities: [1200]

And not all applications require dedicated optimization solvers. Evaluate your workload against the following indicators:

Adoption Recommended
  • [✓] Business rules change frequently (weekly, monthly, or campaign-driven).
  • [✓] Conditions exhibit mutual cross-effects (co-requirements, anti-affinity).
  • [✓] The objective is global score maximization within strict resource caps.
  • [✓] Operational teams demand structured root-cause reports when no solution exists.
Current Implementation Sufficient
  • [-] Filtering consists purely of independent scalar checks (e.g., price < $50).
  • [-] The candidate pool is small (≤ 10 items) and rules are static year-round.
  • [-] First-match greedy picking satisfies all commercial metrics.
  • [-] Engineering cycles are not constrained by recurring rule change tickets.
